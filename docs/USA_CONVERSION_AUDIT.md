## Current application architecture

### Platform

- Next.js 16.2.11 / React 19
- TypeScript
- Supabase authentication and database
- OpenAI Responses API for report generation
- ClickFunnels webhook for paid-access provisioning

### Customer access

Paid access is independent from the assessment schema.

- `app/api/access/status/route.ts` checks Supabase `paid_users`.
- `app/api/clickfunnels/webhook/route.ts` upserts purchasers into `paid_users`.
- Existing customer access can therefore remain intact while the assessment and report are replaced.

This area should not be redesigned as part of the US conversion unless required by a separate access-control change.

### Assessment storage

`app/assessment/page.tsx` stores assessments in Supabase:

- table: `assessments`
- `answers`: JSON
- `scores`: JSON

Generated reports are stored in:

- table: `reports`
- `report_text`: JSON string

Because the core assessment/report payloads are JSON, the US conversion can use a versioned payload without overwriting older records.

Recommended new payload marker:

```ts
assessment_version: "usa-v1"
```

The report renderer should detect the marker and use the US renderer for new records while preserving the existing fallback for legacy records.

## Current assessment implementation

Primary files:

- `app/assessment/page.tsx`
- `lib/assessment/energy-model.ts`
- `lib/assessment/questions.ts`

The current assessment is largely implemented as one large client page. It contains field state, conditional display, AI generation, photo processing, persistence and navigation in the same component.

The current energy model is international and mixed-market. It includes Ireland, UK, EU, US and Other country options and contains metric/European assumptions such as square metres, litres of heating oil, U-values and boiler-oriented heating choices.

Current US defaults already exist, including a $0.18/kWh electricity default, but they are not a dedicated US model.

## Current deterministic logic

`lib/assessment/energy-model.ts` currently calculates:

- estimated annual electricity use from bill and unit-rate inputs
- appliance kWh estimates
- a simple heat-loss index
- fabric band
- largest estimated fabric loss area
- simple risk scores
- rule-based solar suitability
- short rule-based recommendations

Useful pieces can be retained conceptually, but the current scoring does not satisfy the USA Master Specification.

Key conflicts with the specification:

1. Equipment/home age contributes directly to improvement scores.
2. Window U-value can directly elevate window recommendations.
3. Solar sizing is currently suggested from annual electricity use once basic roof fields are present.
4. US HVAC, water-heating, pool, spa, garage, well, irrigation, EV and hidden-load branching is not represented at the required depth.
5. Propane is not a first-class fuel.
6. Heating oil uses litre-based inputs rather than US gallons/spend logic.
7. ZIP-derived climate context is absent.
8. Property-control logic only partially handles apartments and does not yet distinguish condo/HOA/shared-control cases.

## Current AI logic

Primary routes:

- `app/api/generate-assessment-ai/route.ts`
- `app/api/generate-report/route.ts`

The detailed AI route already contains several useful guardrails, including:

- apartment rooftop-solar suppression
- unknown-roof solar caution
- avoidance of exact guarantees
- use of homeowner language
- photo evidence treated cautiously

However, cost, saving and payback values are currently generated by the AI model. This directly conflicts with the Master Specification requirement that deterministic calculations be performed in code and passed to the model as validated inputs.

The current AI schema also forces fixed quantities of recommendations (for example exactly 3 quick wins and multiple upgrade items). The US specification instead requires suppression of trivial/unsupported items and concise limits, so empty or shorter groups must be allowed.

## Current report renderer

Primary file:

- `app/report/[id]/page.tsx`

The renderer already:

- loads the assessment and latest report for the authenticated user
- parses historical JSON report text
- hides rooftop solar for apartments
- supports both older/basic and newer/detailed AI report shapes
- renders cost, saving and payback values from the AI output

This makes backward compatibility practical. The US renderer should be introduced as a version-aware path rather than replacing the legacy parser immediately.

Required US report groups:

- Your Home Energy Snapshot
- Top Priorities
- $0 Quick Wins
- Low-Cost Fixes
- Investigate Next
- Consider Later
- Fuel-Specific Findings
- Solar / Battery / EV when applicable
- Positive Findings
- What to Check Next
- Assumptions & Limits

## Existing-data compatibility strategy

Do not migrate or rewrite existing assessment/report rows.

For new US assessments:

1. Save `assessment_version: "usa-v1"` in the answers JSON.
2. Store expanded US answers in the same `answers` JSON column.
3. Store deterministic analysis and validated recommendation metadata in `scores`.
4. Store AI narrative output in `reports.report_text` as today.
5. Render legacy records with the existing report path.
6. Render `usa-v1` records with the new US report components.

This keeps existing customer history intact and avoids a high-risk database migration.

## Access and production-safety conclusion

Existing purchasers should retain access because the `paid_users` access system is separate from the assessment schema.

During implementation:

- do not change `main`
- work on `usa-conversion`
- keep `international-base` as the permanent preserved baseline
- deploy only a preview/test build from `usa-conversion`
- merge/deploy to production only after US regression scenarios pass

## US implementation plan from this audit

1. Add versioned US assessment types/schema.
2. Build the seven US assessment sections from the Master Specification.
3. Add branching and property-control rules.
4. Add ZIP-derived climate context.
5. Add US HVAC, water-heating, appliance, pool/spa/garage/outdoor, solar/battery/EV and fuel logic.
6. Add recommendation metadata and internal priority scoring.
7. Move cost/savings/payback calculations into deterministic code.
8. Add overlap handling and whole-home savings sanity checks.
9. Replace AI-generated financial values with validated values supplied to the model.
10. Add version-aware US report rendering while retaining the legacy renderer.
11. Add representative US regression scenarios.
12. Run lint/build/tests before production merge.

## Additional audit observations

- `app/dashboard/page.tsx` reads `answers.main_heating_system`, while the current assessment type stores `main_heating`. The US conversion should normalize this when adding version-aware dashboard summaries.
- `lib/assessment/questions.ts` appears to be an older/simple scoring model and is separate from the current main assessment page. It should not be expanded into the US engine; the US engine should live in a dedicated module.
- The current report UI includes a helper that heuristically hides cost for behaviour-like actions. The US implementation should replace that heuristic with explicit recommendation metadata so genuine no-cost actions always render `Cost: $0` and `Payback: Immediate`.
